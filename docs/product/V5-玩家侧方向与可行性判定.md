# V5 · 玩家侧产品方向与可行性判定

> **文档性质**：**可行性判定**（feasibility verdict）。不是 PRD，不是市场结论，也不宣称任何功能「创新」。
> **输入**：用户以玩家视角提出的 12 类功能需求（原文为假设，非用户调研结论）。
> **依据**：核心仓库与站点仓库（`kpl-data-center-site`）**源码级静态盘点** + 2026-10-18/19 落盘数据实测。所有"已有"结论均可点开对应文件复核。
> **上游**：[V5-Phase1-数据与指标规格.md](./V5-Phase1-数据与指标规格.md)（数据层规格，待评审）、[V5-重构决策矩阵.md](./V5-重构决策矩阵.md)（页面决策）、[V4-产品重构路线图.md](./V4-产品重构路线图.md)。
> **未核实项**：虎扑 KPL 数据榜、B 站雷达图视频、第三方 BP 策略网站的存在性与能力，均为用户转述，本文**未独立核实**，不作为论据使用。

## 0. 结论摘要（已替评审锁定，含理由）

用户提出 12 类功能并要求"按最好的效果做"，因此本文不投票、直接定性并锁定本轮范围。

**核心判断：缺的不是数据能力，而是把已有零件组装成玩家路径。**

盘点发现 12 项里有 **6 项在仓库中已有可用零件**（收藏系统、出装聚合、精选规则引擎、逐帧回放、查询表、预测统计），真正从零开始的只有 3 项（周月荣誉、分享图工坊、单局自动叙事卡）。

**锁定决策**

| 决策 | 结论 | 理由 |
|---|---|---|
| 个性化存储 | **localStorage，不引入后端** | 站点是 Cloudflare 静态部署，无服务端；且 `kpl_fav_v1` 收藏机制已存在可复用 |
| 首批玩家入口 | **我的 KPL + 职业哥同款 + 分享图工坊** | 三项复用率最高、数据依赖最低，恰好覆盖"回访 / 学习 / 传播"三条用户价值 |
| 周月荣誉 | **延后到第二批** | 依赖分路评分权重历史回测，是**唯一成本最高**的一项（见 §2.4） |
| 一分钟赛后报告 | **降级为深度内容，不做全站日常功能** | 受分钟级覆盖 2.0% 硬约束（见 §2.2） |
| 自然语言查询 | **本轮不承诺** | 无后端，无法接真 LLM；只能做模板映射，价值有限 |
| 项目阶段约束 | **本轮越权扩张，理由在此留档** | 项目此前定"稳定性验收阶段不再新增大量功能"，本次新增 3 个玩家入口与其冲突，由用户本轮指令覆盖 |

**建议顺序**：B1 分路映射（共同前提）→ 我的 KPL → 职业哥同款 → 分享图工坊。

## 2. 硬约束（与用户提案直接冲突的部分）

### 2.1 站点是静态部署，无后端

证据：`wrangler.toml` + `publish.bat`（Cloudflare Pages / Workers 静态资产）。

**后果**：
- "个性化"、"预测积分记录"、"跨设备同步"、"通知推送" **只能靠 localStorage**，清缓存即丢失，多设备不同步。
- 用户提案中的"带证据的数据问答 / 自然语言查询"**无法在本架构内实现**（没有服务端可放模型或检索）。降级方案只能是"常见问题模板 → 预置查询参数"，不冒充自然语言。

### 2.2 分钟级覆盖 ≈ 2.0%（红线）

实测：可用序列 **221 局 / 全量 11,126 局**；站内逐帧回放 **211 局 / 62 场**。

**后果**：
- "一分钟看懂比赛""历史名场面搜索""战术 DNA""英雄成长曲线""翻盘路径"**都不是全站日常功能**，只能对具备 `has_timeline` 的局开放。
- 现有 `build_picks.py` 的 202 局样本**已接近该上限**，继续在同类数据上加功能边际收益递减。
- 任何此类页面必须标注样本范围，**禁止缺失填充**（该红线已在 V5-Phase1 §B2 固化）。

### 2.3 B1 · 分路映射未修 —— 四条功能的共同地基

证据：站点 `build_replay_frames.py` 的 `_pos_golds()` 按 `player_name` **姓名排序**取前 5 名金币，而非按 `position` 索引对齐。

**它同时阻塞**：
1. 选手实力档案的"同位置排名"（#3）
2. 本命英雄对局助手的"同路对位"（#5）
3. 复盘页的分路经济曲线
4. 周最佳"按实际出场位置归属"（#9）

**结论**：B1 必须在任何"同位置"类功能动工前完成，否则是在错对齐的数据上做更好看的图。

### 2.4 周月荣誉是成本最高的一项，不是最便宜的一项

表面看它只是一个榜；实际按 [V5-Phase1 §5.4](./V5-Phase1-数据与指标规格.md) 必须先完成：
- 分路评分**权重的历史回测**
- 指标**冗余检查**（相关系数 > 0.8 合并）
- **敏感性分析**（权重 ±20% 时排名波动）

且规格明确禁止"随手选几个权重就宣称真实选手实力"。因此它与"我的 KPL"这类页面组装不是一个量级的工作。

### 2.5 没有排位赛数据（产品边界，必须写进页面而非脚注）

数据源只有官方赛事接口（`data/history/*`）。**职业赛与排位赛的英雄选择、装备思路、团队协同环境不一致**。

**强制要求**：「职业哥同款」页面必须在**正文显著位置**标注"这是职业实战记录，不是排位上分推荐"，不得让用户误读为最优方案。

### 2.6 项目阶段约束冲突（已记录，供复盘）

项目此前确立"进入稳定性验收与模型可靠性提升阶段，不再新增大量功能"。本轮新增 3 个玩家入口与其冲突。按用户本轮指令（"按照最好的效果做"）执行，但**冲突本身留档**，以便后续判断该约束是否应正式修订。

## 4. 明确不做与延后条件

**本轮不做**
- 后端、账户体系、跨设备同步、通知推送
- 自然语言问答 / 带证据的 LLM 解释
- 时间序列相似检索（受 2% 覆盖限制）
- 排位赛数据接入（数据源不存在）
- 把收藏、出装、精选对局重新实现一遍（只用现有零件）

**延后条件（满足才重启）**
- 周月荣誉：B1 完成 **且** 分路评分权重回测通过
- 一分钟赛后报告：仅在具备时间轴的局上开放，且界面标注覆盖率
- 自定义条件检索：需先明确"条件是终局字段（可全站）还是时序字段（仅 2%）"，并分别给出覆盖率

**需真实用户验证才能定优先级的事项**（用户已自行提出，本文认可）
- 12 项需求的优先级来自公开产品与社区讨论，属**假设**，不是市场结论
- 页面埋点（查询完成率 / 完整复盘点击率 / 收藏率 / 分享率 / 一周回访率）应在本轮上线后接入

**顺带修掉的一个口径错误（非本次功能引入）**
「数据说明」页（[about.html](../../kpl-data-center-site/about.html)）原文会显示「新口径：最近 **0** 局」。
根因：[build_data.py](../../kpl-data-center-site/build_data.py) 读的是 `train_status.json` 的 `holdout_n_battles`，而 V12 训练状态已不再写这个键 → 站点拿到 0。
修法：改读 backtest 报告里真实的 holdout 对局列表长度（`len(backtest["holdout_battles"])`，实测 = 20），与 [build_predict_data.py](../../kpl-data-center-site/build_predict_data.py) 的口径一致；已同步修正已生成的 `assets/data.js`。线上验收：`holdoutN = 20`，页面文案恢复为「最近 20 局」。

**已修复：模型产物在 sklearn 1.9 下无法加载，`--full` 链路整体不可用（本轮根治）**
现象：[build_data.py](../../kpl-data-center-site/build_data.py) 跑到「名局复盘」就挂，报 `KeyError: 'minute'`。
根因链（三层，缺一层都不会这么难查）：
1. **环境（真正的根源）**：这台机器上有**两个解释器、两套 sklearn**——
   - `Python 3.14.4`：sklearn **1.8.0**，加载模型正常。`build_live_data.py --watch 30`、`official_match_monitor.py`、10-18 22:29 那次训练跑的都是它。
   - `Python 3.12`（即 PATH 上的 `python`）：sklearn **1.9.1**，**所有** HGB 类产物加载失败。
   sklearn ≤1.8 编译出的 Cython 损失类，其 `__module__` 被写成顶层名 `_loss`；1.9 已不再暴露该顶层名 → `joblib.load` 抛 `ModuleNotFoundError: No module named '_loss'`。实测 v5–v9 全部产物同因失败（`v4_realtime_lr.joblib` 例外，它不含该损失类）。
   所以「同一个脚本，换个 python 就跑不通」——上一次成功重建（data.js `generatedAt 2026-10-19 00:12`）用的必然是 3.14。
2. **无错误处理**：[kpl_official_core.py](../../02-KPL实时胜率预测系统/scripts/kpl_official_core.py) 的 `load_model()` 直接 `joblib.load`，没有任何兜底或日志。
3. **静默降级**：`_replay_v11_timeline()` 把异常吞掉后返回**没有任何列**的空 DataFrame，调用方再无条件取 `tl["minute"]` —— 真正的错误信息在最后一层被压成了 KeyError。

修法：在 `load_model()` 里、`joblib.load` 之前登记模块别名 `sys.modules["_loss"] = sklearn._loss._loss`。**只登记模块别名，不触碰任何模型参数**，因此不影响已发布的评估口径。

验收：`python build_data.py` 全链路跑通（末行 `featured=ok timeline=21`）；真实重建后 `holdoutN` 仍为 20、模型版本 V12；`data.js` / `details.js` 的 diff 仅剩生成时间戳与浮点末位噪声；本地 `_regress.js` 五层、线上 L2/L4 全通过（`线上 data.js holdout 局数 = 20`）。

附带收益：`watch_site_data.py --quick --push` 本身跑在 3.12 下，此前它那条链上任何依赖模型的重建都在静默失败；别名补上后一并恢复。

仍建议收敛（本期未做）：「同一个脚本换解释器就跑不通」是这台机器上最大的隐患。长期应让站点脚本统一使用训练时的解释器（3.14 / sklearn 1.8.0），或直接锁 `scikit-learn==1.8.0`。模块别名只保证**能加载**，不保证 1.9 下的推理数值与训练环境长期一致——本次重建的 diff 只有浮点末位噪声属实测结论，不应视为长期保证。
